# 연속 프레임의 파손 검출을 물리적 파손 이벤트로 변환하기

> 공간·시간 기반 Tracking 후처리와 주행 속도 기반 추론 주기 최적화

## 핵심 요약

파손 검출 모델은 동일한 점자블록을 연속된 여러 프레임에서 반복 검출하지만, 서비스에서는 물리적 파손 하나당 하나의 이벤트가 필요하다. 이를 해결하기 위해 공간 tracking, 최소 3회·0.2초의 시간 기반 확정, 점자블록 ROI 관계, confidence와 프레임 품질 검증을 적용했다.

실제 주행 영상 5개에서 `damage_candidate`가 포함된 2,386개 프레임을 물리적 파손 통과 32회에 대응하는 32개 이벤트로 변환했다. 실제 파손 누락 0건, 중복 0건, Event Recall 100%, Event Precision 100%를 기록했으며 모든 이벤트는 최소 4회·평균 9.5회의 유효 관찰을 근거로 생성됐다.

이벤트화 품질을 먼저 검증한 뒤 현재 주행 조건에서 추론 주기를 30 FPS에서 5 FPS까지 낮췄다. 동일한 이벤트 품질을 유지하면서 추론 대상 프레임을 83.3% 줄였지만, 이는 전체 시스템 부하 감소가 아닌 추론 호출량 감소를 의미한다. 최종 FPS와 시간 파라미터는 라인트레이싱 완성 후 실제 주행 속도에서 다시 확정한다.

## 1. 배경

로봇은 한 대의 카메라 영상을 이용해 점자블록을 따라 주행하면서 파손 후보도 검출한다. 초기에는 파손을 놓치지 않기 위해 카메라 입력 30 FPS 전체를 모델에 전달했다.

그러나 모델의 출력 단위는 프레임이고 서비스가 필요한 단위는 물리적인 파손 블록이다. 로봇이 하나의 파손을 통과하는 동안 같은 대상이 수십 개 프레임에서 반복 검출되므로 모든 프레임을 추론해도 새로운 파손 정보가 그만큼 증가하지 않는다. 또한 같은 카메라와 엣지 장비를 라인트레이싱이 공유하기 때문에 파손 검출의 불필요한 전체 프레임 추론은 제어 파이프라인과 연산 자원을 경쟁할 수 있다.

따라서 목표를 다음 두 단계로 변경했다.

1. 프레임 단위 검출을 누락·오탐·중복 없는 물리적 파손 이벤트로 변환한다.
2. 이벤트 품질을 유지하는 범위에서 현재 주행 속도에 필요한 최소 추론 FPS를 찾는다.

## 2. 이벤트 품질 요구사항

파손 이벤트 생성에서 가장 중요한 조건은 다음 세 가지다.

1. 실제 파손으로 검출된 대상은 반드시 이벤트로 남아야 한다.
2. 하나의 물리적 파손은 하나의 이벤트로 생성되어야 한다.
3. 파손이 아닌 대상과 순간 오검출은 이벤트로 남지 않아야 한다.

이를 다음 이벤트 단위 지표로 평가했다.

| 지표 | 정의 |
|---|---|
| Event Recall | 실제 파손 중 최소 한 건의 이벤트로 생성된 비율 |
| Event Precision | 생성 이벤트 중 실제 파손과 대응한 비율 |
| 중복 이벤트 | 하나의 실제 파손에서 두 건 이상 생성된 추가 이벤트 수 |
| 추론 대상 프레임 | 모델 추론을 수행한 전체 프레임 수 |

모델의 이미지 단위 precision·recall은 학습 단계의 성능이며, 이 문서에서는 모델 출력 이후 실제 서비스 이벤트가 올바르게 형성되는지를 평가한다.

## 3. 초기 문제

파손 검출 결과를 즉시 이벤트로 저장하면 다음 문제가 발생한다.

- 동일 파손이 연속 프레임 수만큼 중복 저장된다.
- 순간적인 오검출도 이벤트가 된다.
- 같은 파손에 서로 다른 촬영 시점과 위치가 여러 개 저장된다.
- 흔들리거나 멀리 보이는 프레임이 대표 이미지가 될 수 있다.
- 전체 프레임 추론이 라인트레이싱과 공유하는 연산 자원을 사용한다.

Confidence 임계값만 높이는 것으로는 해결할 수 없었다. Confidence는 단일 프레임의 검출 신뢰도만 나타내며, 여러 프레임의 결과가 같은 물리적 파손인지 판단하지 못하기 때문이다.

## 4. 후처리 파이프라인

### 4.1 공간 Tracking

`DamageEventPipeline`은 연속된 검출을 물리적 파손 후보 track으로 묶는다.

- 한 프레임에서 겹치는 damage box 병합
- 같은 점자블록 ROI에 속한 damage box 그룹화
- 기존 track과 새 검출의 IoU 및 중심점 거리 비교
- 이전 이동 속도를 이용한 bounding box 위치 예측
- 한 검출을 하나의 track에만 할당

이 과정으로 프레임마다 조금씩 이동하거나 크기가 달라지는 동일 파손을 하나의 후보로 유지한다.

### 4.2 시간 기반 확정

한 번의 검출을 즉시 이벤트로 만들지 않고 다음 조건을 적용한다.

| 파라미터 | 현재 설정 | 역할 |
|---|---:|---|
| `confirm_count` | 3회 | 최소 반복 관찰 횟수 |
| `confirm_window_sec` | 2.0초 | 관찰 횟수를 집계하는 시간 범위 |
| `min_confirm_duration_sec` | 0.2초 | 후보가 유지되어야 하는 최소 시간 |
| `min_observation_interval_sec` | 0.1초 | 인접 검출을 다시 세는 최소 간격 |
| `candidate_timeout_sec` | 1.2초 | 마지막 검출 후 track 종료 대기 |
| `reported_track_cooldown_sec` | 10.0초 | 저장된 대상의 재이벤트 억제 |

최소 3회, 0.2초 이상 유지된 후보만 confirmed 상태가 된다. 일시적으로 검출이 빠져도 1.2초 동안 같은 track을 유지하며, 저장된 track은 10초 동안 재보고하지 않는다.

### 4.3 점자블록 관계 검증

```text
require_tactile_roi_for_event = True
tactile_relation_iou = 0.01
group_by_tactile_unit = True
```

`damage_candidate`만 검출됐다고 이벤트를 만들지 않는다. 파손 box가 `tactile_block` ROI와 연결된 경우에만 최종 이벤트 후보가 될 수 있다. 같은 점자블록 안의 여러 damage box는 하나의 분석 단위로 그룹화한다.

### 4.4 Confidence 이중 기준

```text
detection_threshold = 0.225
minimum_event_confidence = 0.375
```

낮은 임계값으로 track을 시작해 실제 파손의 초기 검출을 보존하되, track 전체에서 confidence 0.375 이상의 근거를 한 번도 얻지 못하면 이벤트로 만들지 않는다.

### 4.5 검증된 대표 이미지 선택

Track의 최초 프레임을 바로 저장하지 않는다. 다음 조건을 만족하는 프레임 중 점자블록이 더 가깝고 크게 보이는 이미지를 대표값으로 선택한다.

- 점자블록 ROI의 최소 크기와 면적 충족
- 프레임 경계에 지나치게 걸리지 않음
- 충분한 선명도 확보
- 연속 프레임에서 ROI 크기와 중심점이 안정적임
- 안정적인 ROI가 최소 2회 관찰됨

위치도 이벤트 종료 시점의 최신 좌표가 아니라 대표 프레임 촬영 시점의 좌표를 저장한다. 이를 통해 이미지와 위치의 시점을 일치시킨다.

현재 구현 성과는 track 안에서 ROI 크기·선명도·안정성을 검증한 대표 이미지를 선택한다는 점이다. 대표 이미지는 가장 선명한 프레임으로, 위치는 가장 가까운 검증 프레임 시점으로 각각 선택하는 구조는 별도 후속 설계이며 현재 성과에 포함하지 않는다.

### 4.6 가장 강조할 구현 포인트

#### 1. Tracking만으로 끝내지 않음

Bounding box를 연결하는 공간 tracking만으로 이벤트를 확정하지 않았다. 다음 시간 조건을 함께 적용해 순간 detection과 지속적으로 관찰되는 실제 후보를 구분했다.

```text
confirm_count = 3
min_confirm_duration_sec = 0.2
min_observation_interval_sec = 0.1
candidate_timeout_sec = 1.2
reported_track_cooldown_sec = 10.0
```

최소 반복 횟수와 지속 시간을 만족해야 이벤트 후보가 되고, 일시적인 검출 누락은 timeout 안에서 같은 track으로 유지하며, 이미 보고한 track은 cooldown 동안 다시 이벤트로 만들지 않는다.

#### 2. Recall과 중복을 동시에 관리

중복을 줄이기 위해 필터 조건을 강하게 만들면 실제 파손까지 제거될 수 있다. 따라서 이벤트 수 감소만 보지 않고 실제 파손 보존 여부와 중복을 함께 평가했다.

```text
Event Recall = 100%
중복 이벤트 = 0건
```

실제 파손 32회를 모두 이벤트로 보존하면서 동일 파손의 반복 검출만 하나의 이벤트로 통합했다는 점이 핵심이다.

#### 3. 점자블록과 파손의 관계를 검증

Damage box만으로 이벤트를 만들지 않고 실제 점자블록 ROI와 연결된 파손인지 확인했다.

```text
require_tactile_roi_for_event = True
```

점자블록과 관계가 확인되지 않은 damage 검출은 track이 반복되더라도 최종 이벤트로 저장하지 않아 모델의 원시 오탐이 서비스 이벤트로 바로 전달되는 것을 방지한다.

#### 4. Track 전체에서 대표 이미지를 선택

최초 검출 프레임이나 마지막 프레임을 그대로 저장하지 않는다. Track 전체에서 점자블록 관계, ROI 크기, 선명도와 안정성 조건을 통과한 검증 프레임을 대표 이미지로 선택한다.

대표 이미지와 위치를 서로 다른 프레임에서 독립적으로 선택하는 구조는 후속 개선안이다. 따라서 현재 구현 성과는 **검증된 대표 이미지 선택**까지로 한정한다.

FPS 조정은 위 후처리로 Event Recall과 중복 성능을 먼저 확보한 뒤 수행한 부가 최적화다. 현재 주행 조건에서는 동일한 이벤트 품질을 유지하면서 30 FPS 대비 추론 대상 프레임을 83.3% 줄였다.

## 5. 주행 속도를 기준으로 한 튜닝

### 5.1 현재 사전 검증 조건

| 항목 | 설정값 |
|---|---:|
| 카메라 입력 | 30 FPS |
| 위치 추정에 사용한 주행 속도 | 0.10 m/s |
| 기준 주행 명령 | 0.40 |
| 해상도 | 1280×720 |

`drive_speed=0.40`은 모터 명령 비율이며 실제 m/s가 아니다. 현재 거리 환산에는 launch에 설정된 추정 속도 0.10 m/s를 사용했다. 영상에 wheel odometry가 없으므로 이는 실측 속도가 아닌 사전 검증 기준값이다.

### 5.2 FPS에 따른 이동 거리

| 추론 FPS | 추론 간격 | 0.10 m/s에서 프레임 사이 이동 |
|---:|---:|---:|
| 30 | 약 0.033초 | 약 0.33 cm |
| 15 | 약 0.067초 | 약 0.67 cm |
| 10 | 0.1초 | 약 1 cm |
| 5 | 0.2초 | 약 2 cm |

후처리는 0.1초 이내의 검출을 별도 관찰로 계산하지 않는다. 따라서 30 FPS로 모든 프레임을 처리해도 가까운 프레임 상당수는 이벤트 확정 관점에서 중복된 입력이다. 5 FPS에서는 각 추론이 0.2초 간격이므로 시간적으로 독립된 관찰 후보가 된다.

## 6. 주행 영상 실험

### 6.1 데이터와 방법

`주행시야 녹화본` 폴더에서 파생·주석 영상을 제외한 고유 주행 영상 5개를 사용했다.

- 총 영상 길이: 640.97초(10분 40.97초)
- 원본: 30 FPS, 1280×720
- 모델: v4 ONNX
- Detection confidence: 0.225
- Tracking 및 품질 조건: 배포 launch 설정과 동일

사용자 검토에 따라 마지막 station을 제외하고 damage로 검출된 블록은 실제 파손으로 판단했다. FPS별 track 발생 시간도 대조하여 동일한 물리적 대상인지 확인했다.

### 6.2 5 FPS와 15 FPS 반복 검증

| 영상 | 5 FPS 이벤트 | 15 FPS 이벤트 | 시간 구간 대조 결과 |
|---|---:|---:|---|
| `20260808_163235.mp4` | 7 | 8 | 15 FPS에 마지막 station 오탐 1건 추가 |
| `drive_record_20260808_1049.mp4` | 6 | 6 | 동일 파손 구간 대응 |
| `drive_record_20260808_1055.mp4` | 6 | 6 | 동일 파손 구간 대응 |
| `drive_record_20260808_1105.mp4` | 7 | 7 | 동일 파손 구간 대응 |
| `drive_record_20260808_1114.mp4` | 6 | 7 | 15 FPS에서 같은 파손의 중복 track 1건 |
| **합계** | **32** | **34** | 15 FPS 추가분은 station 오탐 1건과 중복 1건 |

`drive_record_20260808_1114.mp4`의 15 FPS 추가 track은 `5.0~12.4초`와 `7.9~25.5초`로 구간이 겹쳤으며 화면 검토 결과 같은 파손 블록이었다.

### 6.3 완주 영상의 30 FPS 비교

실제 파손 7개가 확인된 `20260808_163235.mp4`는 30 FPS 전체 추론도 추가로 수행했다.

| 추론 FPS | 처리 프레임 | 실제 파손 이벤트 | Station 오탐 | 중복 | Event Recall |
|---:|---:|---:|---:|---:|---:|
| 5 | 782 | 7/7 | 0 | 0 | 100% |
| 15 | 2,344 | 7/7 | 1 | 0 | 100% |
| 30 | 4,687 | 7/7 | 1 | 0 | 100% |

30 FPS와 15 FPS 모두 실제 파손을 추가로 발견하지 않았고 station 오탐 1건이 이벤트로 확정됐다. 5 FPS에서도 실제 파손 7개가 모두 이벤트로 생성됐으며 station은 최종 이벤트가 되지 않았다.

Station에서는 대부분 damage box가 tactile ROI와 연결되지 않아 제거됐다. 일부 프레임에서는 station 영역이 `tactile_block`과 `damage_candidate`로 동시에 오검출되어 관계 조건이 성립했다. 15·30 FPS에서는 이 장면이 반복 관찰 조건까지 충족했지만, 5 FPS에서는 3회 확인 조건을 채우지 못했다. 이는 낮은 FPS가 일반적으로 오탐을 제거한다는 의미가 아니며, station 문제는 별도 class·위치·주행 상태 기반 정책으로 해결해야 한다.

### 6.4 이벤트 형성 결과

현재 0.10 m/s 조건에서 5 FPS 결과는 다음과 같다.

| 지표 | 결과 |
|---|---:|
| 주행 영상 | 5개 |
| 물리적 파손 통과 | 32회 |
| 생성된 파손 이벤트 | 32건 |
| 누락 | 0건 |
| 중복 | 0건 |
| Station 오탐 이벤트 | 0건 |
| Event Recall | 100% |
| Event Precision | 100% |
| 이벤트당 평균 유효 관찰 | 약 9.5회 |
| 최소 유효 관찰 | 4회 |

이벤트 확정에 필요한 최소 관찰은 3회이며 5 FPS에서도 최소 4회, 평균 9.5회를 확보했다.

## 7. 개선 효과

### 7.1 프레임 검출을 물리적 파손 이벤트로 변환

비전 후처리의 핵심 성과는 FPS 감소 자체가 아니라 모델의 프레임 단위 출력을 서비스가 사용할 수 있는 물리적 파손 단위로 변환한 것이다.

5 FPS로 처리한 주행 영상 5개에서는 `damage_candidate`가 포함된 프레임이 총 2,386개였지만 실제 파손 통과는 32회였다. 공간 tracking과 시간 기반 확정을 적용한 결과 2,386개의 양성 프레임이 32개의 파손 이벤트로 집계됐다.

```text
파손 검출 프레임 2,386개
→ 공간 tracking 및 시간·ROI 검증
→ 물리적 파손 통과 32회에 대응하는 이벤트 32건
```

이는 프레임당 하나의 이벤트를 저장한 것이 아니라 반복된 검출을 실제 대상 단위로 정상화한 결과다.

### 7.2 누락 없이 중복 제거

초기 30 FPS 전체 추론과 비교해 5 FPS에서도 실제 파손 Event Recall 100%와 중복 0건을 유지했다. 즉 FPS를 낮추면서 파손 이벤트의 필수 요구사항을 훼손하지 않았다.

| 이벤트 품질 지표 | 결과 |
|---|---:|
| 실제 파손 통과 | 32회 |
| 최종 파손 이벤트 | 32건 |
| 누락 | 0건 |
| 중복 | 0건 |
| Event Recall | 100% |
| Event Precision | 100% |

중복을 억제하는 조건이 강하면 실제 파손까지 제거될 수 있다. 이번 결과는 Recall을 희생해 이벤트 수를 줄인 것이 아니라 실제 파손을 모두 보존하면서 동일 파손의 반복 출력만 통합했다는 점에서 의미가 있다.

### 7.3 반복 관찰에 근거한 이벤트 확정

최종 이벤트는 단일 프레임의 판단으로 생성되지 않았다.

| 관찰 지표 | 결과 |
|---|---:|
| 이벤트 확정 최소 요구 | 3회 |
| 실제 이벤트의 최소 유효 관찰 | 4회 |
| 실제 이벤트의 평균 유효 관찰 | 약 9.5회 |

모든 이벤트가 최소 요구치보다 많은 시간적 근거를 확보했다. 이를 통해 순간 검출과 지속적으로 관찰되는 파손 후보를 구분했다.

### 7.4 오탐의 서비스 이벤트 전파 억제

마지막 station 구간에서는 원시 `damage_candidate` 검출이 존재했고, 일부 프레임에서는 station이 `tactile_block`으로도 검출돼 두 box의 관계가 성립했다. 5 FPS에서는 이 후보가 3회 반복 관찰과 나머지 이벤트 확정 조건을 모두 충족하지 못해 저장 단계까지 전달되지 않았다.

```text
원시 station 오탐
→ 점자블록 관계·시간·confidence·ROI 품질 검증
→ 최종 이벤트 생성 차단
```

이는 이번 영상에서 확인된 후처리 효과이며, 낮은 FPS가 일반적으로 station 오탐을 제거한다는 의미는 아니다. Station이 충분히 반복 검출되면 조건을 통과할 수 있으므로 별도 class 또는 위치·주행 상태 기반 제외 정책이 필요하다.

### 7.5 대표 이미지와 위치의 일관성

Track의 최초 또는 마지막 프레임을 무조건 저장하지 않고, 점자블록 관계·선명도·크기·안정성 조건을 통과한 프레임 중 가까이 보이는 이미지를 대표값으로 선택했다. 위치도 대표 이미지 촬영 시점의 값을 함께 저장한다.

따라서 다음 두 구조적 문제를 해결했다.

- 하나의 파손에 프레임마다 서로 다른 위치가 저장되는 문제
- 저장 이미지와 위치가 서로 다른 시점의 값이 되는 문제

다만 영상에 위치 원시 로그와 실제 파손 측량 좌표가 없어 위치 오차의 정량적 개선값은 계산하지 않았다.

### 7.6 저장 실패 시 이벤트 유실 방지

이벤트는 저장 성공 후에만 `acknowledge`된다. 저장이 실패하면 candidate를 즉시 제거하지 않고 다시 내보낼 수 있어, 중복 억제 과정에서 실제 파손 이벤트가 유실되는 것을 방지한다. 이는 장애 상황을 재현한 정량 결과가 아니라 저장 파이프라인의 구조적 안정성 개선이다.

### 7.7 추론 요구량 감소

완주 영상 기준 처리 프레임은 다음과 같이 감소했다.

```text
30 FPS: 4,687프레임
 5 FPS:   782프레임

감소율 = (4,687 - 782) / 4,687 × 100
       ≈ 83.3%
```

따라서 다음과 같이 표현할 수 있다.

> 실제 파손 Event Recall 100%와 중복 0건을 유지하면서 모델 추론 호출량과 추론 대상 프레임을 30 FPS 대비 83.3% 줄였다.

이는 전체 프로그램의 CPU·GPU 사용률이나 지연이 83.3% 감소했다는 의미가 아니다. 카메라 캡처, 라인트레이싱, 모터 제어, 통신과 녹화는 계속 실행되므로 전체 시스템 부하는 Jetson 통합 실행 환경에서 별도로 측정해야 한다.

### 7.8 시간적으로 중복된 추론 감소

완주 영상에서 30 FPS는 5 FPS보다 약 6배 많은 프레임을 처리했지만 이벤트당 평균 유효 관찰은 약 12.6회와 9.5회로 약 1.33배 차이에 그쳤다.

이는 0.1초 이내의 검출을 독립 관찰로 계산하지 않는 시간 로직 때문에 높은 FPS의 상당 부분이 이벤트 형성에 중복된 입력이었음을 보여준다.

## 8. 결론과 최종 튜닝 시점

현재 사전 검증에서는 0.10 m/s 주행 조건에서 5 FPS가 이벤트 품질을 유지한 가장 낮은 테스트 설정이었다. 주행 영상 5개에서 물리적 파손 통과 32회를 누락과 중복 없이 32개 이벤트로 형성했다.

그러나 5 FPS를 모든 주행 상황의 고정 최적값으로 확정할 수는 없다. 파손 이벤트 후처리 조건은 다음 주행 특성에 직접 영향을 받는다.

- 실제 평균·최대 주행 속도
- 출발·정차 및 가감속
- 코너 회전에 따른 카메라 이동
- 영상 흔들림과 조도 변화
- 파손 블록의 화면 체류 시간
- 프레임 사이 bounding box 이동량

따라서 최종 튜닝은 라인트레이싱이 완성되어 실제 주행 속도와 패턴이 안정된 후 수행해야 한다.

```text
라인트레이싱 안정화
→ 실제 속도·가감속 확정
→ 영상 timestamp와 odometry 수집
→ 파손별 화면 체류 시간 측정
→ 추론 FPS 결정
→ tracking·confirm·timeout·cooldown 조정
→ Event Recall·Precision·중복률 재검증
```

최종 운영값은 다음 조건을 만족하는 설정 중 가장 낮은 FPS로 선택한다.

```text
Event Recall = 100%
중복 이벤트 = 0건
오탐 이벤트 = 0건 또는 허용 기준 이하
```

현재 결과의 정확한 의미는 다음과 같다.

> 카메라 30 FPS 전체 추론이 파손 이벤트 생성에 필수적인 것은 아니며, 추론 주기는 라인트레이싱이 결정한 주행 속도와 대상의 화면 체류 시간을 기준으로 조정할 수 있다. 약 0.10 m/s의 현재 영상에서는 5 FPS가 Event Recall 100%와 중복 0건을 유지한 최소 검증값이었다. 최종 운영값은 라인트레이싱 완성 후 실제 주행 조건에서 재검증해 확정한다.

## 9. 검증 한계

- 0.10 m/s는 영상에서 측정한 실속도가 아니라 launch의 위치 추정 기준값이다.
- 모든 영상이 같은 실내 코스와 유사한 조도에서 촬영됐다.
- Jetson 통합 실행 환경의 CPU·GPU 사용률, 전력, 온도와 제어 지연을 FPS별로 측정하지 못했다.
- 따라서 확인된 개선은 전체 시스템 부하 감소가 아니라 이벤트 품질을 유지한 추론 호출량 감소다.
- 다른 속도·노면·조도에 대한 일반화는 라인트레이싱 완성 후 추가 검증해야 한다.
