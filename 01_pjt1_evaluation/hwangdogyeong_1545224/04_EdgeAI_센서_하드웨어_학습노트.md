# Jetson과 센서 하드웨어를 찾아본 내용

## 1. AI 담당인데 하드웨어도 본 이유

우리 프로젝트의 모델은 서버에서만 돌지 않고 실제 로봇의 Jetson에서 카메라 영상을 받아야 한다. AI 모델만 학습해 두면 끝일 줄 알았는데, 카메라 FPS가 낮거나 Jetson이 뜨거워져 성능이 떨어지면 모델이 좋아도 실시간으로 쓸 수 없다는 것을 알게 됐다. LiDAR나 IMU 데이터와 촬영 시점이 맞지 않으면 파손 위치도 틀어질 수 있어서 하드웨어 쪽도 같이 찾아봤다.

아직 장치를 직접 조립하거나 수치를 측정한 단계는 아니다. 이번에는 팀원과 이야기할 때 필요한 구조와 확인 항목을 먼저 정리했다.

- Jetson Orin Nano에서 AI 추론이 동작하는 과정
- 2D LiDAR를 이용한 거리 측정과 장애물 감지 원리
- 카메라, IMU, 휠 엔코더, GPS/GNSS의 역할
- ROS 2에서 센서 데이터와 AI 추론 결과를 연결하는 방법
- 모터와 Jetson의 전원 분리, 발열, 저장 공간 등 하드웨어 제약
- 센서 이상과 통신 장애를 고려한 안전 동작

## 2. 전체 하드웨어 구성 이해

```text
RGB 카메라 ──────────────┐
                         │
2D LiDAR ────────────────┤
                         │
IMU·휠 엔코더·GPS ───────┤→ Jetson Orin Nano → AI 추론·ROS 2·서버 통신
                         │
라인 센서·범퍼 센서 ─ MCU┘
                         │
                    모터 드라이버 → 좌·우 모터
```

각 장치의 역할은 다음과 같이 구분한다.

| 장치 | 주요 역할 | AI 담당자가 확인할 내용 |
|---|---|---|
| Jetson Orin Nano | 영상 추론, ROS 2 처리, 이벤트 저장 및 통신 | FPS, 지연시간, 메모리, 발열 |
| RGB 카메라 | 점자블록과 파손 영역 촬영 | 해상도, FPS, 노출, 흔들림, 설치 각도 |
| 2D LiDAR | 주변 거리 측정과 장애물 감지 | scan 범위, 최소 거리, 노이즈, 가림 |
| IMU | 가속도와 각속도 측정 | 진동, 방향 변화, bias |
| 휠 엔코더 | 바퀴 회전량과 이동거리 측정 | 미끄러짐, 누적 오차 |
| GPS/GNSS | 실외 절대 위치 추정 | 위치 오차, 수신 불량, 갱신 주기 |
| 라인 센서 | 점자블록 경로 추종 보조 | 햇빛과 바닥색 변화 |
| MCU | 모터 제어 및 긴급 동작 | Jetson과의 통신, watchdog |
| 모터 드라이버 | 모터 속도와 방향 제어 | 전류, 발열, 전기적 노이즈 |
| 배터리/DC-DC | 각 장치에 안정적인 전원 공급 | 전압 강하, 용량, 보호회로 |

## 3. Jetson Orin Nano 학습 내용

### 3.1 프로젝트에서의 역할

Jetson Orin Nano는 로봇 내부의 Edge AI 컴퓨터로 사용한다. 주요 작업은 다음과 같다.

- 카메라 프레임 입력
- 이미지 전처리
- YOLO Detection 또는 Segmentation 추론
- 연속 프레임 결과 확인
- 대표 이미지와 파손 전후 영상 저장
- GPS, 경로 ID, 촬영 시각 결합
- ROS 2 노드 실행
- 파손 이벤트의 서버 전송
- 통신 장애 시 로컬 임시 저장

모터를 직접 정밀 제어하는 일은 실시간성과 안전성 때문에 MCU가 담당하고, Jetson은 높은 수준의 판단과 AI 연산을 담당하는 구조가 적합하다.

### 3.2 Edge AI 배포 흐름

```text
학습 PC의 PyTorch 모델
  → ONNX 변환
  → 변환 전후 출력 비교
  → TensorRT 엔진 생성
  → Jetson에서 FP16 추론
  → 카메라 실시간 입력 연결
  → 전체 파이프라인 지연시간 측정
```

TensorRT 변환 후에는 단순히 실행되는지만 확인하지 않고 원본 모델과 예측 결과가 크게 달라지지 않는지 검증해야 한다.

### 3.3 성능 측정 항목

- AI 모델 단독 추론 FPS
- 카메라 입력부터 결과 출력까지 end-to-end FPS
- 평균, p50, p95 latency
- CPU/GPU 및 메모리 사용량
- 전력 모드별 성능 차이
- 장시간 동작 시 온도와 thermal throttling
- 영상 저장 중 프레임 드롭
- ROS 2 노드 간 메시지 지연
- 통신 장애 중 로컬 저장 공간 증가량

### 3.4 발열과 냉각

AI 추론을 지속하면 모듈의 온도가 상승하고 일정 온도 이상에서는 성능이 낮아질 수 있다. 짧은 테스트의 FPS만 확인하면 실제 장시간 순찰 성능을 잘못 판단할 수 있다.

확인해야 할 내용:

- 방열판과 냉각팬 설치
- 케이스 내부 공기 흐름
- 카메라와 센서 케이블이 팬을 막지 않는지 확인
- 일정 시간 추론 후 클럭과 온도 기록
- 여름철 실외 환경을 고려한 장시간 테스트

### 3.5 저장 공간 관리

정상 영상을 모두 저장하면 저장 공간이 빠르게 부족해진다. 따라서 메모리 또는 로컬 저장장치에 순환 버퍼를 두고 파손 이벤트가 발생할 때만 전후 프레임을 보존한다.

```text
최근 N초 영상 순환 저장
  → 파손 후보 발생
  → 이전 구간 + 이후 구간 저장
  → 대표 이미지 생성
  → 위치·시간 정보 결합
  → 서버 전송 완료 후 보관 정책 적용
```

## 4. LiDAR 학습 내용

### 4.1 기본 원리

LiDAR는 레이저를 발사하고 물체에 반사되어 돌아오는 정보를 이용해 주변 물체까지의 거리를 측정한다. 2D LiDAR는 한 평면을 회전하며 각도별 거리값을 생성한다.

ROS 2에서는 일반적으로 다음과 같은 형태의 scan 데이터를 다룬다.

- 측정 시작·종료 각도
- 각 측정값 사이의 각도 간격
- 각도별 거리 배열
- 측정 가능한 최소·최대 거리
- 데이터가 측정된 시각

### 4.2 장애물 감지

로봇 전방의 특정 각도 범위를 관심 구역으로 정하고, 그 범위 안에 안전거리보다 가까운 점이 존재하는지 확인한다.

```text
전방 영역에 장애물 없음 → 정상 주행
감속 거리 안에 장애물 존재 → 감속
정지 거리 안에 장애물 존재 → 즉시 정지
일정 시간 후 경로 확보 → 재출발
경로 미확보 → 우회 또는 관리자 알림
```

단일 거리값만으로 정지하면 먼지나 반사 노이즈 때문에 오작동할 수 있다. 일정 개수 이상의 연속된 측정값, 여러 scan의 지속 여부, 범퍼 센서 등을 함께 확인하는 것이 안전하다.

### 4.3 LiDAR의 한계

- 유리, 검은색 물체, 강한 햇빛 등 재질과 환경에 따라 측정이 불안정할 수 있다.
- 센서 높이보다 낮은 장애물이나 센서 평면 위·아래의 물체를 놓칠 수 있다.
- 로봇 몸체나 케이블이 scan을 가릴 수 있다.
- 사람의 다리처럼 움직이는 물체는 scan마다 위치가 달라진다.
- LiDAR만으로 장애물 종류를 알기는 어렵다.

따라서 LiDAR는 주로 안전거리 확보와 장애물 존재 확인에 사용하고, 필요하면 카메라 정보와 결합한다.

### 4.4 설치 시 고려사항

- 로봇 몸체가 scan 영역을 가리지 않는 위치
- 진동이 적고 수평을 유지할 수 있는 고정 구조
- 보행자 다리와 주요 장애물을 감지할 수 있는 높이
- 회전부 및 케이블 간 간섭 방지
- 센서 좌표계와 로봇 기준 좌표계의 위치·회전값 측정

## 5. 카메라 학습 내용

### 5.1 카메라 설치

점자블록 파손을 인식하려면 점자블록이 충분한 픽셀 크기로 촬영되어야 한다. 너무 넓은 시야각은 주변을 많이 볼 수 있지만 작은 균열의 픽셀 수가 줄어든다.

확인할 항목:

- 카메라 높이와 하향 각도
- 점자블록이 프레임에서 차지하는 면적
- 해상도와 FPS
- 렌즈의 초점거리와 왜곡
- 주행 진동과 motion blur
- 자동 노출과 화이트밸런스 변화
- 역광, 그림자, 야간 환경
- 필요 시 보조 조명 사용

### 5.2 카메라 캘리브레이션

렌즈 왜곡을 보정하고 이미지 좌표와 실제 공간의 관계를 구하려면 카메라 캘리브레이션이 필요하다. 정확한 크기나 거리 추정이 필요한 경우 카메라 내부 파라미터와 설치 위치를 확인해야 한다.

### 5.3 프레임 품질 검사

AI 추론 전에 다음과 같은 저품질 프레임을 확인할 수 있다.

- 지나치게 어둡거나 밝은 프레임
- blur가 심한 프레임
- 점자블록이 화면에서 너무 작은 프레임
- 카메라가 가려진 프레임
- 이전 프레임과 내용이 거의 동일한 프레임

저품질 프레임은 즉시 파손으로 판단하지 않고 재촬영 또는 다음 프레임 확인을 요청하는 편이 안전하다.

## 6. IMU와 휠 엔코더

### 6.1 IMU

IMU는 가속도와 각속도를 측정해 로봇의 움직임과 방향 변화를 파악한다. 하지만 센서의 작은 오차가 적분되면서 방향과 위치 오차가 커질 수 있다.

주의할 점:

- 정지 상태의 bias 측정
- 모터와 노면 진동 영향
- 센서 축 방향 확인
- 급회전과 충격 상황
- timestamp와 단위 확인

### 6.2 휠 엔코더

엔코더는 바퀴 회전량을 측정해 이동거리와 회전량을 계산한다. 좌우 바퀴의 이동량 차이로 로봇의 방향 변화를 추정할 수 있다.

오차 원인:

- 바퀴 미끄러짐
- 좌우 바퀴 지름 차이
- 노면 요철
- 급가속과 급정지
- 엔코더 tick 누락

IMU와 엔코더를 함께 사용하면 서로의 단점을 일부 보완할 수 있지만 시간이 지나면 누적 오차가 발생하므로 LiDAR 기반 위치 추정이나 GPS와 결합해야 한다.

## 7. GPS/GNSS와 위치 정보

GPS는 야외 절대 위치를 제공하지만 건물, 나무, 날씨와 위성 상태에 따라 오차가 발생할 수 있다. 같은 점자블록 파손도 매번 다른 좌표로 기록될 가능성이 있다.

중복 이벤트를 병합할 때 사용할 정보:

- GPS 좌표와 오차 반경
- 점검 경로 ID
- 경로 시작점부터의 이동거리
- 로봇 지도 좌표
- 촬영 시각
- 이미지 특징 유사도
- 이전 파손 이벤트의 위치와 상태

GPS 좌표만 완전히 동일한 경우를 같은 위치로 판단해서는 안 된다.

## 8. 센서 퓨전과 좌표계

각 센서는 서로 다른 좌표계에서 데이터를 생성한다.

- `base_link`: 로봇 몸체 기준
- `laser`: LiDAR 기준
- `camera_link`: 카메라 기준
- `imu_link`: IMU 기준
- `odom`: 시작점부터 누적된 이동 기준
- `map`: 전체 지도 기준

센서가 로봇 중심에서 얼마나 떨어져 있고 어느 방향으로 회전되어 있는지 변환 관계를 정의해야 한다. 이 값이 틀리면 지도상의 장애물과 카메라에서 본 위치가 서로 맞지 않는다.

센서 퓨전에서 중요한 것은 값뿐 아니라 **시간**이다. 카메라 이미지, LiDAR scan, IMU, 엔코더 데이터의 timestamp가 맞지 않으면 움직이는 로봇에서 서로 다른 시점의 데이터를 결합하게 된다.

## 9. ROS 2 노드 구성 학습

기능을 독립된 노드로 분리하면 각 부분을 테스트하고 교체하기 쉽다.

```text
camera_node ─→ vision_inference_node ─→ event_manager_node ─→ server_client_node
                         │                     ↑
lidar_node ─→ obstacle_node ─→ safety_node     │
                         │                     │
imu/encoder/gps ─→ localization_node ─────────┘
                         │
                  motor_control_node(MCU 통신)
```

예상 역할:

- `camera_node`: 카메라 프레임 발행
- `vision_inference_node`: YOLO 추론과 결과 발행
- `event_manager_node`: 연속 프레임 확인, 대표 이미지와 영상 저장
- `lidar_node`: LiDAR scan 발행
- `obstacle_node`: 감속·정지 구역의 장애물 판단
- `localization_node`: IMU, 엔코더, GPS 정보 결합
- `safety_node`: 긴급정지와 재출발 조건 관리
- `server_client_node`: 이벤트 업로드와 재전송 관리

AI 추론이 느려져도 안전 정지가 늦어지지 않도록 장애물 감지와 긴급정지 경로는 AI 이벤트 처리와 분리해야 한다.

## 10. 전원 설계 학습

### 10.1 전원 분리

모터는 시작하거나 부하가 커질 때 순간적으로 많은 전류를 사용한다. 이때 전압이 떨어지거나 전기적 노이즈가 발생하면 Jetson이 재부팅되거나 카메라와 센서 연결이 끊길 수 있다.

따라서 다음을 고려한다.

- 모터 전원과 Jetson·센서 전원 경로 분리
- 장치의 입력 전압에 맞는 DC-DC 사용
- 충분한 전류 공급 여유 확보
- 메인 퓨즈와 장치별 보호
- 역극성, 과전류, 과전압 보호
- 공통 접지와 노이즈 경로 검토
- 모터 전원선과 카메라·통신선 배선 분리
- 긴급정지 버튼 구성

### 10.2 배터리 용량

배터리 사용시간은 단순히 Jetson 소비전력만으로 계산하지 않고 모터, LiDAR, 카메라, 통신 모듈, 냉각팬과 DC-DC 손실을 모두 포함해 추정해야 한다.

```text
예상 사용시간 ≈ 실제 사용 가능한 배터리 에너지 / 시스템 평균 소비전력
```

계산값에는 안전 여유를 두고 실제 주행 부하에서 측정해야 한다. 배터리 전압이 낮아지면 갑자기 꺼지기 전에 서버에 상태를 알리고 로봇이 안전한 위치에 정지하도록 한다.

## 11. 통신과 장애 대응

Wi-Fi 또는 LTE 연결은 주행 중 끊길 수 있다. 통신이 끊겨도 로봇이 안전하게 정지하거나 제한된 동작을 계속할 수 있어야 한다.

- 파손 이벤트는 로컬 큐에 임시 저장
- 이벤트마다 고유 ID 부여
- 전송 성공 응답을 받은 데이터만 완료 처리
- 재연결 시 순서대로 재전송
- 같은 이벤트의 중복 저장 방지
- 저장 공간이 부족할 때의 우선순위 정책
- 정상 영상은 기존 순환 버퍼 정책에 따라 폐기

## 12. 안전 설계

AI 모델은 오탐과 미탐이 발생할 수 있으므로 사람과의 충돌을 막는 최종 안전장치로 사용하지 않는다.

안전 계층:

1. 물리적 긴급정지 버튼
2. MCU watchdog 및 통신 끊김 정지
3. 범퍼 센서 접촉 감지
4. LiDAR 기반 감속·정지
5. 소프트웨어 속도 제한과 상태 머신
6. 관리자 원격 정지

Jetson의 AI 프로그램이 멈추더라도 MCU가 모터를 안전하게 정지할 수 있어야 한다.

AI와 하드웨어가 독립적으로 개발되더라도 다음 값은 팀에서 미리 합의해야 한다.

- 모든 장치의 timestamp 기준
- 감속 거리, 정지 거리, 최대 속도
- AI 결과 메시지의 bbox/mask, confidence, class
- 파손 이벤트 데이터 구조
- Jetson과 MCU 사이의 명령 및 상태 프로토콜
- 통신 장애와 재부팅 시 복구 방식

## 15. 찾아보고 나서 중요하다고 느낀 점

- AI 모델의 정확도만으로 프로젝트가 완성되지 않으며 카메라 설치, 전원, 발열과 센서 동기화가 실제 성능에 큰 영향을 준다.
- Jetson은 AI와 상위 수준 처리를 담당하고, 모터 제어와 최종 안전 정지는 MCU가 담당하는 구조가 적합하다.
- LiDAR는 장애물 존재와 거리를 빠르게 확인할 수 있지만 센서 평면 밖의 장애물과 재질별 측정 한계가 있다.
- GPS만으로 동일 파손 위치를 판별하기 어려워 엔코더, IMU, 경로 ID와 이미지 유사도를 함께 사용해야 한다.
- 센서 데이터는 좌표계와 timestamp가 정확히 맞아야 결합할 수 있다.
- 모터 전원 변화와 노이즈가 Jetson과 카메라에 영향을 줄 수 있으므로 전원 분리와 실제 부하 테스트가 필요하다.
- AI 추론이 중단되더라도 장애물 감지와 긴급정지 기능은 독립적으로 동작해야 한다.
- 다음 단계에서는 각 장치를 실제로 연결한 뒤 FPS, 온도, 거리 오차, 프레임 드롭과 전원 안정성을 수치로 기록해야 한다.
