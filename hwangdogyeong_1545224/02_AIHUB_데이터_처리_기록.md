# AI Hub 데이터 확인 및 처리 기록

팀에서 AI Hub의 `보행 안전을 위한 도로 시설물 데이터`를 받았는데, 압축 파일이 크고 안쪽에도 ZIP이 여러 개 있어서 먼저 구조부터 확인했다. 전체를 무작정 풀기보다 점자블록 라벨이 실제로 몇 개인지, 정상과 불량은 어떻게 표시되어 있는지 확인하는 것을 이번 작업의 목표로 잡았다.

## 1. 데이터 출처

- 데이터명: 보행 안전을 위한 도로 시설물 데이터
- 구축 연도: 2021년
- 형식: JPG/JPEG 원천 이미지, 이미지별 JSON 라벨
- 라벨 유형: 바운딩박스 및 세그멘테이션
- 점자블록 공개 통계: 30,000장(정상 14,850장, 불량 15,150장)
- 출처: https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=513

AI Hub의 전체 데이터는 30종 시설물을 포함하므로 프로젝트에 필요한 점자블록 클래스만 선별해야 한다.

## 2. 내려받은 파일 확인

먼저 받은 파일은 원천 이미지가 아니라 **Training 라벨 배포 ZIP**이었다. 바깥 ZIP 안에는 `TL1.zip`부터 `TL33.zip`까지 33개의 라벨 압축 파일이 포함되어 있었고, 각 내부 ZIP에는 시설물·상태별 폴더와 이미지별 JSON이 저장되어 있었다.

현재 데이터 확보 상태는 다음과 같다.

| 구분 | 상태 |
|---|---|
| Training 라벨 | 배포 ZIP 확보, 내부 `TL1~TL33` 구조와 JSON 통계 확인 |
| Training 원천 이미지 | `TS8`, `TS9` 다운로드 중, 아직 완료되지 않음 |
| Validation 라벨 | 아직 확보하지 못함 |
| Validation 원천 이미지 | 아직 확보하지 못함 |

따라서 지금 확인한 내용은 **라벨 파일 기준**이다. 원천 이미지가 없으므로 이미지가 실제로 열리는지, JSON의 `filename`과 이미지가 정확히 짝을 이루는지, polygon이 이미지 위에서 올바르게 표시되는지는 아직 확인하지 못했다.

확인한 JSON 주요 필드:

- `info`: 이미지 ID, 촬영일, 지역 ID, 파일명, 너비, 높이
- `description`: 시설물 코드, 하위 분류, 상태 코드
- `annotations`: 라벨 ID/이름, 파손 여부, 주석 종류, bbox 또는 polygon 좌표

## 3. 내가 처리한 방법

압축을 전부 풀면 시간과 저장 공간이 많이 필요해서, 바깥 ZIP 안의 ZIP을 하나씩 읽는 스크립트를 작성했다. 이 과정에서 다음 내용을 확인하도록 했다.

1. 바깥 ZIP에서 내부 라벨 ZIP 목록을 탐색한다.
2. 경로 또는 라벨명에 `점자블럭/점자블록`이 포함된 JSON만 선별한다.
3. 정상/불량 분포, annotation type, label name, 이미지 크기를 집계한다.
4. JSON 파싱 오류와 필수 정보 누락을 기록한다.
5. 후속 이미지 매칭과 데이터 분할에 사용할 CSV 매니페스트를 만든다.
6. 실행 결과를 JSON과 Markdown 프로파일로 저장한다.

## 4. 실행 방법

PowerShell 기준:

```powershell
python .\황도경_1545224\scripts\inspect_aihub_tactile.py `
  --archive "C:\Users\사용자\Downloads\119.보행 안전을 위한 도로 시설물 데이터.zip" `
  --output-dir .\황도경_1545224\results
```

스크립트는 Python 표준 라이브러리만 사용한다. 원본 데이터는 용량과 배포 조건 때문에 Git에 올리지 않고, 코드·통계·매니페스트만 관리한다.

## 5. 데이터 품질 점검 기준

- JSON의 `info.filename`이 비어 있지 않은가
- 이미지 너비와 높이가 0보다 큰가
- annotation에 `is_defect`, `annotation_type`, 좌표가 존재하는가
- 같은 `image_id` 또는 파일명이 중복되는가
- 정상/불량 상태와 annotation의 파손 여부가 모순되지 않는가
- bbox 좌표가 이미지 범위 안에 있는가
- polygon의 점 개수가 유효한가

현재 스크립트는 데이터 구조와 분포를 빠르게 확인하는 1차 점검 도구이다. 실제 학습 전에 원천 이미지 압축을 연결해 파일 존재 여부, 좌표 범위, 손상 이미지 로딩까지 추가 검증해야 한다.

### 라벨 배포 ZIP 실행 결과 (2026-07-15)

- 내부 학습 라벨 ZIP: 33개
- 전체 검사 JSON: 817,586개
- 선별한 점자블록 이미지: 23,475개
- 점자블록 annotation: 51,721개, 모두 polygon
- annotation 상태: 정상 11,560개 / 불량부분 28,246개 / 불량전체 11,915개
- 중복 image ID 및 filename: 0개
- JSON 파싱 오류: 1개

AI Hub 소개 페이지의 점자블록 30,000장은 전체 구축 통계이고, 이번에 확인한 압축은 경로가 `1.Training/라벨링데이터`인 학습 라벨 묶음이다. 따라서 23,475장을 전체 데이터 수와 직접 비교해 누락이라고 판단하지 않고, Validation 라벨 또는 별도 배포 파일을 추가 확인해야 한다. 또한 한 이미지에 여러 polygon이 존재할 수 있어 annotation 수는 이미지 수보다 많다.

파싱 오류 1건은 `TL10.zip`의 보도(시멘트 콘크리트) 정상 JSON으로, 점자블록 대상 밖이다. 스크립트는 오류를 기록하고 나머지 파일 처리를 계속했다.

처음에는 AI Hub 페이지에 적힌 점자블록 30,000장이 라벨 압축 안에서도 그대로 나올 줄 알았다. 실제로 돌려 보니 23,475장이 나와서 스크립트가 잘못된 줄 알고 경로를 다시 확인했다. 현재 받은 파일이 전체 데이터가 아니라 Training 라벨 묶음이라는 것을 확인했고, 이미지 수와 annotation 수가 다른 이유도 한 이미지에 polygon이 여러 개 들어갈 수 있기 때문이라는 것을 알게 됐다. 아직 원천 이미지와 Validation을 받지 못했으므로 이 수치를 최종 학습 데이터 수로 사용하면 안 된다.

## 6. 학습 데이터로 변환할 때의 기준

- bbox 탐지 실험: JSON bbox를 YOLO 형식의 정규화된 `class x_center y_center width height`로 변환
- 세그멘테이션 실험: polygon 좌표를 YOLO segmentation 또는 COCO polygon으로 변환
- 상태 분류: 정상/불량 라벨을 사용하되 파손 영역 crop과 전체 이미지 분류를 비교
- 분할: 촬영일·지역·연속 구간을 묶어 train/validation/test 간 유사 이미지 누수 방지
- 클래스 정의: `normal`, `defect` 두 클래스로 먼저 시작하고 세부 파손 유형은 실제 라벨 분포 확인 후 확장

## 7. 이번에 내가 한 부분

- AI Hub 배포 파일의 중첩 압축 구조와 JSON 스키마를 확인했다.
- 프로젝트 대상인 점자블록 라벨만 자동 선별하는 전처리 코드를 작성했다.
- 데이터 상태·주석·크기 분포와 파싱 오류를 재현 가능하게 산출하도록 했다.
- 원본 대용량 데이터는 저장소에서 제외하고 결과와 코드만 공유하는 방식으로 정리했다.
- 후속 모델 학습에 필요한 누수 방지 분할, bbox/segmentation 변환, 품질 검증 항목을 정의했다.

여기까지는 라벨 구조를 확인하고 전처리 방향을 잡은 단계이다. 원천 이미지 매칭, 실제 mask 시각화, train/validation 분할과 모델 학습은 아직 진행하지 않았다.

## 8. 추가로 받고 있는 데이터: 인도보행 영상

기존 데이터만으로도 점자블록 정상/파손 학습은 가능하지만, 실제 로봇은 점자블록만 크게 찍힌 사진이 아니라 사람, 자전거, 볼라드와 여러 노면이 같이 나오는 환경에서 움직인다. 이런 실제 보행 환경의 차이를 보완할 수 있는지 확인하기 위해 AI Hub의 `인도보행 영상` 데이터도 다운로드하고 있다.

- 데이터명: 인도보행 영상
- AI Hub 번호: 189
- 구축 연도: 2019년
- 전체 구축량: 약 67만
- 데이터 형식: 이미지와 XML 어노테이션(Depth Prediction 제외)
- 출처: https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=189
- 현재 상태: 다운로드 중, 아직 전체 파일 검수 및 전처리는 하지 않음

### 페이지에서 확인한 데이터 구성

| 데이터 종류 | 공개 구축량 | 우리 프로젝트에서 볼 부분 |
|---|---:|---|
| Bounding Box | 35만 | 사람·자전거·차량·볼라드 등 보행 장애물 |
| Polygon | 10만 | 장애물의 조금 더 정확한 형태 |
| Surface Masking | 5만 | 점자블록과 인도 노면의 normal/damaged mask |
| Depth Prediction | 17만 | 스테레오 영상 기반 거리 정보, 후속 검토 |

Surface Masking에는 `braille_guide_blocks`라는 점자블록 라벨과 `normal`, `damaged` 속성이 포함되어 있다. 이 부분은 우리 프로젝트의 점자블록 정상/파손 분할 학습에 직접 사용할 수 있을 것으로 보인다.

장애물 데이터에는 사람, 자전거, 자동차, 오토바이, 유모차, 휠체어 같은 이동체와 볼라드, 벤치, 기둥, 화분, 가로수 같은 고정체가 들어 있다. 파손 탐지 모델에 이 29종을 전부 섞기보다는 LiDAR 기반 장애물 감지와 카메라 보조 인식이 필요한지 하드웨어·자율주행 담당자와 먼저 정리해야 한다.

## 9. 두 데이터셋을 같이 쓸 때의 계획

두 데이터셋 모두 점자블록 파손을 포함하지만 그대로 한 폴더에 합치면 안 된다고 생각했다. 기존 `보행 안전을 위한 도로 시설물 데이터`는 이미지별 JSON이고, 새 `인도보행 영상`은 XML과 Surface Masking 구조라서 먼저 공통 형식으로 맞춰야 한다.

### 우선 진행할 순서

1. 다운로드가 끝나면 ZIP 개수와 전체 용량을 확인한다.
2. XML의 `braille_guide_blocks` 중 `normal/damaged` 샘플을 각각 시각화한다.
3. mask가 점자블록 전체를 표시하는지, 실제 파손 부분만 표시하는지 확인한다.
4. 기존 JSON polygon과 새 XML polygon을 같은 내부 스키마로 변환한다.
5. YOLO Segmentation 형식으로 변환하면서 좌표 범위를 검사한다.
6. 데이터셋 출처, 촬영 구간, 날짜를 기준으로 train/validation/test를 나눈다.
7. 기존 데이터만 학습한 결과와 두 데이터를 합친 결과를 따로 비교한다.

### 공통 내부 라벨 후보

```text
tactile_normal
tactile_defect_partial
tactile_defect_full
```

새 데이터가 파손을 `damaged` 하나로만 구분한다면 억지로 `partial/full`로 나누지 않고, 첫 번째 실험에서는 다음처럼 두 클래스로 단순화하는 방법도 비교하려고 한다.

```text
tactile_normal
tactile_damaged
```

### 주의할 점

- 두 데이터셋의 카메라 높이, 구도와 해상도가 다를 수 있다.
- `damaged`의 기준과 polygon이 표시하는 범위가 서로 다를 수 있다.
- 같은 장소의 연속 프레임이 학습셋과 검증셋에 같이 들어가면 성능이 과대평가될 수 있다.
- 이미지 수가 많은 쪽에 모델이 치우치지 않도록 출처별 비율을 기록해야 한다.
- 사람 얼굴이나 차량 번호판의 비식별화 상태를 확인해야 한다.
- Depth 데이터는 용량이 크고 현재 MVP의 점자블록 파손 탐지에 바로 필요하지 않으므로 우선순위를 낮춘다.

## 10. 현재 생각한 활용 범위

이번 프로젝트에서 바로 사용할 1순위는 Surface Masking의 점자블록 `normal/damaged` 데이터이다. Bounding Box 장애물 29종은 점자블록 파손 모델에 직접 넣는 데이터가 아니라, 카메라 기반 장애물 보조 인식이 필요할 때 별도 모델로 보는 편이 맞다. Depth Prediction 데이터도 LiDAR가 잡지 못하는 낮은 장애물이나 거리 보조가 필요한지 확인한 뒤 사용 여부를 결정하려고 한다.

다운로드가 완료되면 데이터 전체를 사용한다고 바로 정하지 않고, 먼저 점자블록 Surface Masking 샘플과 라벨 수를 확인한 다음 실제 로봇 카메라 환경에 도움이 되는지 작은 베이스라인으로 비교할 계획이다.
